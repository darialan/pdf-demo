架构拆解与设计答辩

一个客户端 DOM 分页与 PDF 导出引擎的完整拆解：架构、流程、数据流、工程机制，以及面试时如何回答"这个库为什么这么设计"。

一句话本质

它不是"把网页截图塞进 PDF"，而是把浏览器的排版结果重新解释成一份可计算的「分页计划」——先用语义协议把 DOM 标注成「可切 / 不可切 / 不打印」，再把 DOM 降维成一维区间，用一个纯函数算出断点，最后按断点切片渲染。真正被"导出"的，是这份计划，而不是 DOM 本身。

01 · 设计动因

为什么这么设计：三个业界病根，对应三个架构决策

面试讲"为什么"不要从代码讲起，要从它替谁解决了什么讲起。这个库的重构提案文档里完整保留了改造前的代码缺陷清单——那是最有说服力的叙事起点。

病根 A

按物理高度硬切，文字与表格行被腰斩

改造前算法「按像素递归节点」，P 节点以固定 1.5px 步长递归，不识别真实文字行。20,000px 单个 P 直接触发 RangeError: Maximum call stack size exceeded。表格行识别还硬编码了 ant4-table-row，而 AntD 默认类名是 ant-table-row，规则根本没命中。

决策 A

语义协议 + 行级测量 + 贪心回退

三重解法：① data-pdf-atomic / splittable / ignore 三标签协议，把"能不能切"从算法里拿出来交给业务声明；② 用 Range.getClientRects() 取每个文本行的真实包围盒，精确到行而非节点；③ paginate() 遇到跨页受保护区就把切点回退到该元素顶部。

病根 B

脱离上下文后样式坍塌，截图与测量不一致

改造前是「先整根节点截图，再从实时 DOM 计算分页点」。页面在截图期间一旦重排（Tab 切换、弹窗、滚动条），图片和断点就会对不上。而 cloneNode(true) 出来的脱离原 CSS 上下文的克隆体，会出现字体变小、行高错位、输入框内容丢失。

决策 B

计算样式全量冻结 + 单一快照贯穿

cloneWithResolvedStyles() 逐节点把 getComputedStyle 冻结到克隆体，并显式搬运 input/textarea/select/canvas 的运行时值。更关键的是：测量对象 === 渲染对象 === 同一份离屏快照，从根上消灭"预览能看、导出不一样"。

病根 C

超长文档一次性截图，Canvas 显存爆仓

改造前整根节点截图，scale = devicePixelRatio × 2，长页面产出几万像素高的超大 Canvas，浏览器直接 OOM 白屏。同时没有任何资源就绪信号、没有总超时、没有取消能力、没有产物校验。

决策 C

按页微切片渲染 + 像素即时释放

废弃整页截图。每次 html2canvas(el, { y, height }) 只截单页正文微片，写入 jsPDF 后立即 canvas.width = 0; canvas.height = 0 释放显存。配套资源预算预检（8M 像素上限）、15s 超时、AbortSignal 取消与逐页 setTimeout(0) 让出主线程。

一句话串场：三个病根分别对应"切不准、切不齐、切爆了"。所以这个库的架构本质是——把"怎么切"这个难题从渲染层彻底剥离到一个纯函数里，渲染层只负责忠实地执行已经算好的切法。

03 · 核心流程

六阶段流水线：从 DOM 到 Blob

这是面试时最该能默画出来的一张图。注意第 ③ 阶段和第 ⑤ 阶段操作的是同一份快照——这是全库一致性的根基。

阶段之间为什么必须串行

② 必须在 ④ 之前——字体没就绪时测出来的行高是错的；④ 必须在 ⑤ 之前——没有受保护区就无从避让；⑤ 必须在 ⑥ 之前——没有断点就无法切片；⑥ 必须在 ⑦ 之前——PDF 页面必须逐页追加。整个顺序不可交换，这正是 prepareLayout() 用同步顺序代码而非 Promise.all 的原因。

为什么测量与渲染共用一份快照

如果测量用实时 DOM、渲染用克隆体（或反过来），两者之间任何一次重排都会让断点与画面错位。prepareLayout() 只克隆一次，把这份快照同时交给 measureDocument() 和 capture()，从结构上消除不一致的可能。

04 · 核心算法

贪心回退避让：整个库技术含量最高的一段

纯函数 paginate(height, capacity, protectedRanges, maxPages)。输入三个数与一组区间，输出无空洞无重叠的 PageSlice[]。

core/pagination/paginator.ts
export function paginate(height, capacity, protectedRanges, maxPages = 100) { if (![height, capacity, maxPages].every(Number.isFinite) || height <= 0 || capacity <= 0) { throw new Error('打印区域或纸张尺寸无效'); } const ranges = protectedRanges .map(range => { if (range.bottom - range.top > capacity) { throw new Error('存在超过单页高度且不可拆分的内容，请缩小图片或调整布局'); } return range; }) .sort((a, b) => a.top - b.top); const pages = []; let start = 0; while (start < height) { if (pages.length >= maxPages) throw new Error(`文档超过 ${maxPages} 页限制，请拆分导出`); let end = Math.min(start + capacity, height); if (end < height) { // Retreat to the beginning of every intersecting line/block, including overlaps. for (;;) { let next = end; for (const range of ranges) { if (range.top < end && range.bottom > end) next = Math.min(next, range.top); } if (next === end) break; end = next; } } if (end <= start) throw new Error('重叠的不可拆分内容超过单页高度，无法安全分页'); pages.push({ start, end }); start = end; } return pages; }

这个算法好在哪（面试答法）

  • 纯函数，零 DOM 依赖。输入三个数，输出区间数组。可以在 Node 里跑精确单测，不需要 jsdom 渲染。
  • 保证不重不漏。下一页起点严格等于上一页终点，测试用例逐页断言了这一点（expect(page.start).toBe(pages[i].end)）。
  • 宁可报错，不静默腰斩。超高原子块、保护区重叠、超过页数上限——全部显式抛错并给出可操作的中文提示。
  • 容差处理。validatePageBreaks() 用 0.25px 容差区分「亚像素舍入」与「真实穿插」，避免浮点误报。
追问预案：「为什么不用二分/DP 求最优解？」——贪心回退追求的是"零腰斩"这一硬约束下的最快收敛，不是页数最优。贪心实现 O(页数 × 保护区数)，DP 需要 O(n²) 区间状态且无法表达"回退"语义。业务上是可接受的折中。
05 · 业务数据流

数据结构如何逐级降维

理解这个库最快的路径，是盯住两个核心结构：Interval[]（DOM 的一维投影）和 PageSlice[]（分页计划）。整条流水线就是这两个数组之间的变换。

快照 cloneWithResolvedStyles 源 HTMLElement 离屏克隆体 锁定源宽度 px，避免脱离流后 shrink-wrap

三种规则的语义分工

ignore
不参与测量、不参与渲染。分页器、导出按钮、调试图层直接出局。
atomic
注册为一个受保护区间。放不下就整块下移；overflow: 'error' 则超高直接报错，'split' 则允许下沉继续拆分。
container
不注册区间，而是继续向内遍历，让内部子元素各自决定命运。
text
用 Range.getClientRects() 拆成逐行区间——文字天然可切，但行与行之间要避开。

capacity 是怎么算出来的

// core/geometry/page-geometry.ts contentWidth = pageWidth - paper.left - paper.right; ratio = contentWidth / width; // pt / CSS px bodyTop = paper.top + headerHeight + 6; footerY = pageHeight - paper.bottom - 14 - footerHeight; capacity = (footerY - 6 - bodyTop) / ratio;

关键：capacity 会被 / ratio 还原回 CSS px，因为后续所有测量与切点都在 px 空间进行；而写入 PDF 时再乘回 ratio 变回 pt。整条链路只有 ratio 这一个换算因子，所以 px↔pt 永远不会漂移。

06 · 工程化机制

模块划分 · 错误处理 · 扩展点

面试考察的往往不是算法，而是你知不知道自己在维护什么。这一节回答：边界在哪、错误怎么冒出来、别人怎么接进来。

6.1 模块划分的三条硬规则

RULE 01

core 不认识浏览器

core 只接收数值与区间。任何需要 document、getComputedStyle、Range 的能力，一律下沉到 adapters。

RULE 02

第三方库只出现在 adapters

html2canvas、jspdf 声明为运行时依赖，安装本包时自动安装；构建时保留 external，交由消费项目的打包工具解析与复用。react 保留为使用方提供的可选对等依赖。

RULE 03

顺序只在 application 定义

core 回答"怎么算"，application 回答"什么时候算、算完做什么、失败怎么收场"。两层职责不混，是这个库可维护的根本。

资源生命周期：三层释放保证

  • 快照：prepareLayout() 的 cleanup() 挂在 try/catch/finally 三处，出口路径全收。同时从 activeRoots（WeakSet）移除，解除重复提交锁。
  • Canvas：release(canvas) 立即把宽高置 0 释放显存；dispose() 兜底清理所有残留。两者都在 finally 中调用。
  • 调试图层：clearPageBreaks() 按 [data-pdf-debug] 选择器批量移除，并还原临时改写的 position。

防御性设计清单

  • 遍历用显式栈而非递归——绕开 JS 调用栈上限，正是旧实现 20,000px 崩溃的根因。
  • WeakMap 缓存行高，避免同一父元素重复 getComputedStyle。
  • 跨 realm 兼容：isPrintableElement() 用 duck-typing + ownerDocument.defaultView 双重判断，iframe 内的元素也能识别。
  • WeakSet 并发锁阻止同一 DOM 区域被重复提交导出。
  • canvas 像素预算：MAX_PIXELS = 8_000_000，scale 自适应封顶 2，下限 0.5。

07 · 面试答辩

"为什么这么设计" —— 8 问 8 答

每条都给出可直接说出口的答法，并附上代码位置作为证据。面试官追问细节时，你可以当场翻代码。

Q1为什么不直接用 window.print() 或 html2canvas 整页截图？

三者各有硬伤：window.print() 弹出对话框、无法程序化控制产物、依赖用户打印设置；整页截图在长文档上必然 Canvas OOM，且无法保证分页点不切开文字；物理硬切则完全不看语义，表格行必被腰斩。这个库要的是可编程、可校验、低内存的产物，所以只能自己实现"测量—分页—渲染"这条链路。

可补强：重构提案里做过路线对比——服务端 Chromium PDF 可保留文本层但引入服务成本；结构化数据直接绘制 PDF 可搜索但要重写排版。选 html2canvas + jsPDF 是因为业务要复用现有视觉模板，并明确承认"光栅正文不可搜索"是这条路线的已知代价。
Q2为什么要把分页算法做成纯函数？

三个理由：① 可测——paginate() 的 7 个用例在 Node 环境断言精确到小数点的切片边界，不需要 jsdom、不需要浏览器；② 可证一致——预览和导出调用的是同一个函数，所以"预览显示的断点"和"导出的实际断点"在数学上必然相同；③ 可换——将来要改分页策略（比如支持"孤行寡行"或最优页数 DP），只需替换 core 内部，adapters 与 application 完全不动。

可补强：core 层实测零 DOM、零第三方依赖——grep 全部 import 只有 ../types。依赖方向永不反转，这是分层架构真正的价值所在。
Q3为什么测量要基于克隆体，而不是直接测页面上的 DOM？

因为原 DOM 是活的——Tab 切换、滚动条出现、弹窗遮挡、Flex/Grid 弹性宽度变化，都会让它在测量瞬间和渲染瞬间长得不一样。而 html2canvas 本身也可能触发重排。所以流程是：克隆一份 → 冻结计算样式 → 离屏挂载 → 在克隆体上测量，也用同一个克隆体渲染。这样"测量"与"渲染"面对的是同一个不会变的对象。

可补强：克隆并非直接 cloneNode 就完事——cloneWithResolvedStyles() 还要搬运 input/textarea/select/canvas 的运行时值（克隆不复制这些）、把 img.crossOrigin 设为 anonymous（否则 canvas 被污染无法导出）、并锁定根宽度防止 shrink-wrap。
Q4冻结计算样式时，为什么特意跳过 width / height？

因为 getComputedStyle 返回的宽高是使用值（used value），而不是声明值。对一个 width: auto 的盒模型，computed width 是浏览器算出来的具体像素数；把它冻结下来等于把 auto 改写成固定值，这会破坏外边距合并（margin collapsing）和表格对齐——页面会整体走样。

这是细节里的设计。代码注释写得很直白：// Retain authored dimensions from cloneNode/CSS, rather than fixing every box. 正则 /^(min-|max-)?(width|height|block-size|inline-size)$/ 精准排除了这一族属性。能讲出这一条，说明你真的读懂了而不是抄了个轮子。
Q5分页怎么保证不切开文字和表格行？

三步：① 用 data-pdf-atomic / splittable / ignore 把 DOM 标注成三类语义；② 测量时，原子元素整体注册为一个 Interval，文本节点则用 Range.getClientRects() 拆成逐行区间——表格行天然命中 atomic 规则，所以"表格行不腰斩"是算法自然结果而非特判；③ paginate() 遇到切点穿过受保护区，就把切点回退到该元素顶部，并迭代回退直到落在空白缝隙。

关键洞察："能不能切"这件事被从算法里抽出来交给了业务声明。库不猜你是表格还是卡片，它只认协议。这也是为什么它能做成技术无关的——核心规则里没有任何一个组件库的类名。
Q6为什么按页切片，而不是一次性截整张长图？

Canvas 显存与宽高乘积成正比。一张 20000px 高、800px 宽的图在 scale=2 下就是 32000×1600 = 5120 万像素，远超浏览器 Canvas 上限，必然 OOM。改成按页切片后，峰值显存只与单页有关，与文档总页数无关——100 页和 1000 页的峰值内存一样。每页写进 PDF 后立即 width=0; height=0 释放显存，不等 GC。

还有两个配套细节：① MAX_PIXELS = 8_000_000 预算预检，scale 按 min(2, √(预算/面积), 8192/宽, 8192/高) 自适应算，下限 0.5，低于就报错而不是硬渲染；② 每页结束 await setTimeout(0) 让出主线程，避免长任务把 UI 冻住。
Q7这个库的边界在哪？哪些场景它明确不支持？

诚实回答反而加分：① 产物是光栅 PDF，文字不可搜索、不可复制、体积偏大——这是 html2canvas 路线的固有代价；② html2canvas 对 CSS 的支持有边界，复杂滤镜、混合模式可能渲染不准；③ 表格跨页不支持 rowspan、不自动重复表头；④ 文字行测量用的是 getClientRects() 的行盒近似，混合字体下行高不精确（代码注释里明确承认"不是完整的 CSS line-box 重建"）；⑤ 虚拟列表需要业务方自行提供完整数据构造打印视图，库不会去渲染未挂载的数据。

可补强：库的应对是用错误把边界显性化——超高原子块报错、边距占满报错、图片加载失败报错。它不假装支持一切，而是遇到不满足的前提就停下来并给出可操作提示。"明确的能力边界 + 显式失败"本身就是一个成熟的架构信号。
Q8如果让你改进，你会动哪里？

三个按优先级排的改进：① 行盒精度——用 getClientRects() 加行高差值的近似法在混合字体下会偏，改为逐行读取 Range 的实际行盒，或在克隆体上按字体分组测量；② 表头重复——把 thead 做成"每页自动叠加"的语义，在 paginate() 阶段为每页附加固定区段；③ 可选矢量后端——当前 createPdfWriter 是工厂函数，换成走 pdf-lib 的矢量绘制即可保留文本层，而 core 的分页计划完全不用改。

这一问的关键是：改进点全部落在 core 或 adapters 的可替换边界内，没有一处需要推翻分层架构。能说明"为什么这些改动是安全的"，比提出改进本身更能证明你理解了设计。
08 · 已知边界

诚实的短板清单

下面几条来自代码注释与重构提案的实测记录，是这个库当前真实的边界。面试时主动说出来，比被追问出来好得多。

算法与测量精度

  • 文字行高为近似估算：leading = (lineHeight - rect.height) / 2，代码注释明确说明"不是混合字体的完整 CSS line-box 重建"。
  • 贪心回退追求"零腰斩"，不追求页数最优——保护区密集时可能多出空白页。
  • 受保护区重叠且整体高于单页时会直接抛错，而不是尝试拆分。

产物与能力边界

  • 光栅 PDF：文字不可搜索、不可复制，体积大于矢量方案。
  • 不支持跨页 rowspan，不自动重复表头。
  • html2canvas 对 CSS 支持有天然边界（滤镜、混合模式可能失真）。

全局状态与一致性

  • configurePrint() 使用模块级全局状态，同进程内多份配置会互相影响——需用局部的 rules/ruleConfig 覆盖来规避。
  • README 文档中的 PrintSettings.slicingMode 在 core/types.ts 中并不存在，属于文档与类型不一致。
  • 预览一致性校验（validatePageBreaks）用的是 0.25px 容差，亚像素边界可能放行。

工程现状

  • 单测覆盖集中在 core 与 application（14 套 / 44 例），缺浏览器端到端导出、PDF 产物视觉比对、内存基准。
  • 跨域图片依赖 crossOrigin=anonymous，对方服务端未配 CORS 头时会失败并报出具体图片名。
  • overlay 的调试选择器里出现了 .ant-pagination 等具体组件库类名，与 core 层"技术无关"的原则存在轻微不一致。
